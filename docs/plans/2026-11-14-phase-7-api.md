# Phase 7.5 — the read-only JSON API

`docs/PLAN.md` §2 lists «CLI + API» among the MVP artefacts and §10 names `src/fixjury/api/app.py` and
`routes.py`; until now FastAPI existed only inside the review page. This change adds the API the plan
asks for, on the same database, without adding an endpoint that can write.

## Scope

| Step | Deliverable | Proof |
| --- | --- | --- |
| API | `src/fixjury/api/routes.py` — tasks, runs, snapshots, health, all GET | integration tests against live Postgres: filters, pagination, 404s, 422 on an invalid status |
| API | `src/fixjury/api/app.py` — `create_app(maker=...)`, router mounted at `/api/v1` | the app takes its session maker from the caller, like the review page, so it holds no globals |
| CLI | `fixjury api [--host] [--port]` — uvicorn on loopback by default | a real server on `127.0.0.1:8123` answered every route |

## Endpoints

| Method | Path | Returns |
| --- | --- | --- |
| GET | `/api/v1/health` | `{"status": "ok"}`, or 503 when the database does not answer |
| GET | `/api/v1/tasks` | `{tasks, count}` — corpus listing without the issue text |
| GET | `/api/v1/tasks/{task_id}` | the task with `body` and the frozen `spec` |
| GET | `/api/v1/runs` | `{runs, count, total}` with `task`, `agent`, `status`, `limit`, `offset` |
| GET | `/api/v1/runs/{run_id}` | the run with its `diff`, `verdict` and `rejections` |
| GET | `/api/v1/snapshots` | `{snapshots, count}` — the newest snapshot per agent |
| GET | `/api/v1/snapshots/{snapshot_id}` | one stored snapshot, payload included |

## Design

**Read-only by construction, not by policy.** There is no POST/PUT/PATCH/DELETE route, so no browser,
agent or adapter can record a run, a verdict or a snapshot through the API. A test walks
`app.routes` and fails if any method outside `GET`/`HEAD`/`OPTIONS` appears.

**No metric arithmetic.** `/snapshots` serves `metric_snapshots.payload` exactly as stored, which is
what invariant 5 requires: the API is a reader of the numbers, not a second place that computes them.
The test asserts the served payload equals the stored payload, not a recomputation.

**Blindness is untouched.** Runs and verdicts are public data (`§5 Публикация`), so the run detail
includes agent and model. The blind boundary lives in the review page, which still strips them; the API
does not re-open that door because it has no review endpoint at all.

**Pagination is explicit.** A listing carries `count` (this page) and `total` (the filter result), so a
consumer can page without guessing whether it has everything. `limit` is bounded to 500.

**Money stays a decimal string.** `cost_list_usd` and `sandbox_seconds` serialise as strings, the same
shape the snapshot payload uses; a float would round a published number.

## Not done, and why

- **No authentication.** The server binds `127.0.0.1` unless told otherwise and reads only public rows;
  a public deployment needs a reverse proxy and a decision about exposure, which is the same
  owner-approved step as serving the metrics page.
- **Intra-rater kappa** is still blocked on the schema: `verdicts` is keyed by `run_id`, so a second
  blind pass would overwrite the first verdict. That needs a `pass_no` in the key, and `AGENTS.md`
  makes a schema change an ask-first item.
- **OpenHands** remains configuration only (`openhands_image` is empty), so the 96-pair grid is still
  two agents of three.
